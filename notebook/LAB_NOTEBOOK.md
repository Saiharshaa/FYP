**Findings that affect the method**
- The canonical-solution check is partly circular. evalplus computes the
  expected outputs by running the canonical solutions (`get_groundtruth`),
  so 164/164 validates the pipeline, not canonical correctness. The labels
  mean "agrees with the canonical solution on the base+plus inputs". The
  report should state this as a label-quality limitation.
- Timeouts are host-dependent. The per-test limit is max(1 s, 4 × the
  canonical runtime measured on the current host). Timeout labels (an H3
  category) can therefore flip between machines or under load. Label the
  corpus on one fixed host and record it.
- The subprocess backend's network isolation depends on the host. It uses an
  unprivileged network namespace (`unshare --net`) if permitted; otherwise it
  falls back to a Python socket guard, which can be bypassed and is not a
  security boundary.

## 2026-09-28 (later): Phase 1 corpus pipeline, tested with a mock model

**Decisions (user):** build the pipeline only; no real generator model until
TC1 access or budget is confirmed. Sampling: 5 samples × T ∈ {0.2, 0.8} per
problem, i.e. 10 × 163 = 1630 candidates (`[generation]` in config).

**Built** (`verifier.corpus.build`, commit `8a2a220`)
- `generate`: EvalPlus instruct prompt, sent as the user message only (chat
  APIs can't pre-fill EvalPlus's response prefix). It logs via RunLog with
  resume, never executes code (so it is TC1-safe), and refuses a second
  model in the same run_id.
- `label`: evalplus `sanitize`, then `label_many`, then the sandbox
  `categorise`. Writes `corpus.jsonl` and `corpus_meta.json` (machine,
  evalplus commit, dataset version and md5, generation config).
- `MockCoder`: deterministic by seed % 5: 0–2 canonical, 3 `return None`,
  4 syntax error.
- Tests: 72 passed in WSL.

**Full-size dry run** (mock, 1630 candidates): generate 10 s; resume made
0 calls; label 138 s with 6 workers.

**Finding 1: sanitize repairs syntax errors.** evalplus's tree-sitter
`sanitize` drops a broken `return (` line and keeps a docstring-only function,
which returns None and is categorised `wrong_output`. On HE/0 it drops the
whole function, giving a load `error`. The evalplus CLI does the same. So
**syntax errors in model output mostly do not appear as `error`**, which
matters for H3. The labels were left as they are; each row now records
`response_code_parses`, `sanitize_modified` and `response_has_code_block`.
Verifiers must be shown the sanitized `solution` (the labelled code), not the
raw response.

**Finding 2: parallel labelling produces false `fail`s on correct code.** In
the 6-worker dry run, 4 of the 978 byte-identical canonical copies (HE/83 ×1,
HE/139 ×3) got raw status `fail`: they exceeded evalplus's 1.0 s per-test
limit on a test whose canonical reference time is 0.25 s. They were
categorised `slow`, which is how the discrepancy was caught. Other copies of
the same code passed. Relabelling the same log **with 1 worker, twice:
0/978 false fails both times**, and every other label and category was
identical. Serial takes about 275 s versus 138 s.
- Likely cause: this laptop CPU mixes 2 performance and 8 efficiency cores
  (i7-1255U), plus turbo/thermal behaviour, under 6 concurrent evalplus
  workers. The reference times come from one earlier measurement (cached
  pickle).
- This matters for the study: a correct candidate labelled incorrect, which
  a verifier accepts, is scored as a false accept. The noise was about 0.4%
  of correct candidates in this run.
- The labels were not adjusted. **Decision needed**: the labelling policy
  (e.g. serial by default).

**Open questions**
- Labelling concurrency policy (above).
- Should the pickle of reference times be recomputed on the labelling machine
  immediately before labelling, so limits reflect current conditions?
- TC1 generation job script (SLURM + vLLM), once the model is chosen.

**GPU throughput: concurrent requests (2026-11-18).**
- `runlog.execute` was serial, which would leave a vLLM server mostly idle.
- It now takes `concurrency` (default 1, so the pilot's behaviour is
  unchanged). Requests run in a thread pool, but only the main thread writes
  the log, so resume, single-writer and no-duplicate guarantees hold. New
  tests cover equality with serial runs, real overlap, and a failure in the
  middle followed by a resume.
- `configs/aspire_a100.toml` sets 32 for generation and verification
  (proposal), and `scripts/aspire/env.sh` selects it.
- Trade-off to decide: with batching, per-request seeds are still sent, but
  vLLM does not guarantee bit-identical replay. Seeds then index independent
  samples rather than exact replays. The pilot (llama.cpp, `--parallel 1`)
  was exactly replayable.

**Rough GPU budget for the full sweep (estimate, not measured).**
- Calls: 163 problems × 10 candidates = 1,630.
  - Generation: about 1,630 calls × ~300 output tokens ≈ 0.5M tokens.
  - Verification per verifier model: direct + swapped + reason × 3 seeds =
    8,150 calls, ≈ 2–2.5M output tokens.
- Assuming a 7B model in bf16 on one A100 gives 1,000–2,500 tok/s across 32
  concurrent requests, that is under an hour of generation per model pair,
  plus model load. Even 5 model pairs with retries stay around 10–20

## 2026-11-18: strategies (c)/(d) and the RQ4 selection analysis

**User go-ahead (2026-11-18):** implement (c) and (d), which were on hold
since 2026-09-30.

**Design: tests come from the specification, once per problem.**
- The verifier model sees only the problem statement, never the candidate
  and never the hidden tests. Once per (problem, seed) it writes either
  - (c) `self-tests`: `assert` statements, or
  - (d) `reference`: a brute-force `reference(...)` plus a
    `generate_inputs()` returning small argument tuples.
- That output is applied to all 10 candidates of the problem.
- Why: as in CodeT, tests cannot be anchored on one candidate, and it needs
  10× fewer model calls.
- Model calls run in `verify`, so they are fine on a GPU host. All code runs
  in `harness/exec_verdicts` inside the WSL sandbox, writing `exec.jsonl`.
  The report takes these verdicts from execution, not from parsing.
- Cost per candidate is the per-problem call split over its candidates.

**Pre-registered decision rules** (in `strategies/execution.py`, written
before any pilot output was seen):
- (c) accept iff every extracted assert passes. Each assert runs separately
  with a 2 s alarm. A candidate that fails to load is rejected.
- (d) accept iff the candidate agrees with `reference` on every input that
  `reference` itself handles within 2 s. Floats compare at 1e-6 tolerance.
- No usable tests, or no usable reference, means no verdict, which the
  report counts as reject, as for the judge strategies.

**Extractor v2 (post hoc, like parser v2).**
- In the first 8 `self-tests` answers from the 1.5B pilot model, only 4
  contained plain asserts. The others used unittest classes
  (`self.assertEqual`) or doctest `>>>` blocks.
- v2 also converts those, but only when v1 finds nothing, so it never
  overrides v1. It recovers 8/8.
- v1 stays the pre-registered rule. The report shows v2 rows where v2
  changes a verdict. Exec runs v2 only where it differs, so nothing is
  executed twice.

**RQ4 selection analysis** (`analysis/selection.py`, in every report).
- Per problem: random = c/k; verifier = picks uniformly among accepted
  candidates, or randomly if none is accepted; oracle = 1 if any candidate
  is correct. Expected values are exact.
- Headroom captured = (verifier − random) / (oracle − random).
- Pilot (1.5B, self-verification; random 68.2%, oracle 90.0%):

| Strategy | Verifier pick | Headroom captured |
|---|---|---|
| direct (seed mean) | 68.2% | +0.00 |
| direct-swapped | 68.1% | −0.01 |
| reason (seed mean, v1) | 67.8% | −0.02 |
| reason vote, v1 | 69.4% | +0.05 [−0.02, +0.15] |
| reason vote, v2 | 68.4% | +0.01 [−0.02, +0.04] |

- No judgement-only strategy captures any headroom; every CI includes 0.
  This fits H4: below some reliability, verifier-based selection is no
  better than random.
- (c)/(d) pilot running (`scripts/run_pilot_exec.sh`, 240 per-problem calls
  at about 55 s each with the local 1.5B, then sandboxed execution). Results
  to follow.

## 2026-11-19: (c)/(d) pilot result, first evidence for H2

`scripts/run_pilot_exec.sh` finished 23:59: 240 per-problem calls (1.5B,
self-verification, seeds 0–2) and 2,560 sandboxed executions. Report:
`reports/pilot-q15b/report.md`. Base rate 68.2%.

| Strategy | Accuracy | FAR | FRR | MCC | No verdict |
|---|---|---|---|---|---|
| always accept | 68.2% | 100% | 0% | 0 | – |
| (b) reason, single call, v1 | 60.2% | 87.4% | 17.6% | −0.063 | 12.4% |
| (c) self-tests, single call, v1 | 42.7% | 6.0% | 81.2% | 0.168 [−0.009, 0.304] | 15.8% |
| (c) self-tests, v2 extractor | 44.4% | 8.9% | 77.3% | 0.166 [−0.006, 0.314] | 2.5% |
| (d) reference, single call | 55.8% | 18.6% | 56.2% | **0.245 [0.147, 0.347]** | 46.7% |
| (d) reference, 3-seed vote | 58.0% | 6.3% | 58.6% | **0.356 [0.207, 0.503]** | – |

With no-verdict calls excluded: (d) accuracy 74.4%, FAR 37.8%, FRR 20.6%,
MCC 0.404 (560 of 1,200 dropped); (c) v1 45.2%, FAR 7.1%, FRR 77.5%,
MCC 0.190.

**Reading.**
- **Executing code flips the error profile.** Judgement-only strategies
  accept 87–100% of incorrect code. Execution-grounded strategies accept
  6–19%, and (d) is the first strategy whose MCC CI excludes 0. This is the
  direction H2 predicts.
- **The cost of that shift is false rejects.** Most of them come from the
  verifier's own mistakes:
  - (c): wrong expected values in model-written asserts reject 77–81% of
    correct code.
  - (d): 46.7% of executions have no usable reference. 200 of these are
    `no_reference`, matching the 20/120 calls truncated at the 1,536-token
    cap. 100 are `NameError` and 70 `TypeError`; NameError is likely
    `List`/`Tuple` annotations without `from typing import ...`, to check.
  - No verdict counts as reject, so these failures land in FRR.
- **Not yet better than always-accept on accuracy** (base rate 68%). On
  usable outputs, (d) reaches 74.4%.
- **RQ4 selection is still about 0** ((d) +0.05 to +0.07, CIs from −0.3 to
  +0.3). With a high FRR, many problems have no accepted candidate and fall
  back to random.
- **Cost per candidate is lower than (b).** The model writes once per
  problem: 48–63 output tokens per candidate versus 385 for reason, plus
  about 0.2–1 s of sandbox time per candidate.
